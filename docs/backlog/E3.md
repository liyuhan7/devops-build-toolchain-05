## 2. fzy 和 libco 的位置

| 项目 | 使用阶段 | 本次工作 |
|---|---|---|
| fzy，暂按 `jhawthorn/fzy` | E3 及后续各工具的低成本测试 | 固定同一上游 Commit，保留完整可构建源码，准备受控故障和变更分支，运行构建、功能验证、修复行为对照 |
| libco，暂按 `Tencent/libco` | 后续四工具端到端集成 | 记录选型理由与待核验条件；E3 不把它加入必做运行矩阵 |

fzy 官方源码使用 Make 构建，包含 `check` 和需要 Ruby/Bundler 的 `acceptance` 目标。本阶段以 `make`、`make check` 和无终端交互的功能断言为主要路径，降低环境成本。[官方 Makefile](https://github.com/jhawthorn/fzy/blob/master/Makefile)

libco 官方同时提供 Make 和 CMake 路径，后续本组固定使用 Make。[官方 README](https://github.com/Tencent/libco#build)

“libco 有论文实验基础、所选版本没有 Dockerfile”目前沿用选型理由，仍需记录对应论文、项目版本和源码树核验结果。仓库名相同不等于论文版本一致。后续集成开始前还需选定能正常退出的功能测试，不能只运行可能长期等待的服务示例。

### fzy 的自动依赖必须处理

当前查看的上游 Makefile 包含 `-MD` 和 `-include $(OBJECTS:.o=.d)`，会自动补齐头文件依赖。仅从显式规则中删除一个头文件，通常不足以制造 MD。[官方 Makefile](https://github.com/jhawthorn/fzy/blob/master/Makefile)

孙鲲华、管泽昊先为实验副本确定统一策略：限定目标对象文件，在受控版本中禁用对应自动依赖加载或生成，并移除该副本残留的 `.d`，用显式依赖构成可核验基线。保存相对上游的 Patch，说明这样做是故障注入。原始 fzy 构建保留作对照，不声称上游存在本组注入的缺陷。

C0 必须在选定目标、配置与项目文件范围内声明正确。不能关掉全项目自动依赖，却未经检查就宣称全项目没有 MD/RD。报告注明系统头文件、工具链文件是否在判断范围内。

## 4. 三步执行与依赖

### 第一步：统一版本和环境

李宇瀚完成 E3-01，黄骢驰 Review。

1. 确定 fzy 上游完整 Commit SHA，将源码快照与许可证放入 `fixtures/e3/fzy/`；避免嵌套 `.git`。
2. 记录上游 URL、SHA、许可证、获取方式以及相对上游修改。
3. 确定一个 Linux 环境，例如 WSL2 Ubuntu；记录发行版、架构、Git、GNU Make、C 编译器、Python、strace 版本。B 组另外记录 Docker 版本和基础镜像摘要。
4. 在该版本上检查 `make`、`make check`，试跑无交互功能命令，保存失败或成功日志。只有可复跑后才冻结为基准。
5. 在选定目标范围构造声明正确的 C0，记录配置、真实实验提交 SHA、图预期与构建日志。原始上游快照与 C0 的实验改造通过 Patch 分别保留。
6. 统一案例 ID、目录、运行记录格式和人工答案来源。CI 入口作为协作辅助，可由收尾任务补齐，不阻塞实验启动。

Ubuntu 版本和镜像摘要以实际选择为准，不在本计划里编造。Linux 系统调用跟踪不能用 Windows 原生运行代替。只有容器部分需要 Docker，不要求先开通云资源。

四工具不要各复制一份完整 fzy。公共源码快照加各自 Patch 重建案例，运行工作目录放在忽略的 `work/e3/<run-id>/`。每次运行新建目录，不覆盖旧证据。选择提交的小型实验文本日志保存到 `evidence/e3/`；外部课程资料、二进制、镜像导出、缓存和秘密不提交。

每次运行至少保存：

| 文件 | 内容 |
|---|---|
| `run.json` | 案例 ID、操作者、运行时间、操作系统与架构、上游 SHA、实验 SHA、Patch 摘要、配置、证据来源 |
| `commands.json` | 实际命令、工作目录、环境变量覆盖、开始/结束时间、退出码、日志相对路径 |
| `*.stdout.log`、`*.stderr.log` | 对应命令的真实输出，保留导致失败的关键信息 |
| `observations.md` | 预期、实际、是否相符、异常、试过的方法、下一步 |

人工答案放在 `fixtures/e3/<tool>/expected.json`、`oracle.md`；实际观察放在 `evidence/e3/<tool>/<run-id>/`。固定 MD 报告使用 E2 已定义的 Finding 字段，额外的 ORACLE 来源放在外层基线说明或包装字段中，避免向禁止额外属性的公共 Schema 随意加字段。

| C1 | 新增 include 及可观测使用，遗漏对应 Make 依赖 | 一条 introduced MISSING；初次源码变更可能重编译，随后只改新头文件才检验漏重建 |
| C2 | 源码保持 C1，只改编译 recipe 的参数 | C1 的 MD 保持 unchanged；命令变化使旧对象需要重新分析；不能将命令变化本身标成新增 MD |

执行顺序：

1. 李宇瀚在 E3-01 中交付 C0，管泽昊从该版本开始，沿用相同构建配置和判断范围。
2. 管泽昊形成 C1 的真实提交，保存相对 C0 的 diff，验证新增头文件被读取但未声明。孙鲲华 Review 后合并，保留真实历史。
3. 黄骢驰取得 C1，实际构建产生旧对象，再形成只改编译命令的 C2。保留 C1 编译产物进入 C2，记录 C1/C2 的 `make -n -B <选定目标>`，确认编译参数确实改变。
4. 在 C2 先执行普通 make，再在另一个同源码副本做 clean 构建。不要在第一次 C2 增量测试前清理掉旧对象。
5. 参数优先选择会改变既有测试可观察行为的宏，记录普通构建与 clean 结果；如果只改优化参数，至少保存真实命令及是否重编译的证据，不捏造输出差异。
6. 在 C2 之后另作证据提交，填写前三个完整 Commit SHA、配置及源文件 diff。配置变化是此用例的主动输入，预期触发失效或重分析，不沿用 E2“错误配置直接拒绝”作为唯一答案。

**保留三个真实版本：**C0、C1、C2 所在 PR 推荐使用普通 `Create a merge commit` 保留提交，且保留基线分支。不要只 Squash 后删除唯一保存 C0/C1/C2 的分支。C0/C1/C2 的 SHA 是实验版本，PR 合并 SHA 是协作记录，两者分别填写。合并历史中可能有说明或证据提交，“只改编译命令”按 C1/C2 的样本源码树 diff 核验。所有 Git 提交与推送由成员操作。

Issue 验收：三个 SHA 可从远端取得，且按顺序构成历史；C1/C2 源码相同，C2 的命令改变；孙鲲华复核 C1、李宇瀚复核 C2并链接记录。历史图是 ORACLE 预期，不冒充 EChecker 生成的图。

第三条以所选版本实际行为核验，预期输出 `apple` 和退出码 0。正式脚本把输出与固定文本比较，分别保留退出码。只运行 `--help` 或确认二进制存在不足以作为全部功能验证。上游有无交互 `-e` 参数路径，适合容器测试。[官方源码](https://github.com/jhawthorn/fzy/blob/master/src/fzy.c)

PR 2 作者刘洋，Reviewer 陆泓。分支 `test/e3-draft-container`，标题 `test(draft): 记录容器构建失败与参考成功样本`，写 `Closes #实际编号`。

3. 参考候选安装必要工具链，用同一源码、构建命令和功能验证命令复跑。

### E3-05：MDFixer 的固定 MD 与修复验证

PR 1 作者刘君杰，Reviewer 刘洋。分支 `test/e3-repair-input`，标题 `test(mdfixer): 建立固定缺失依赖与参考补丁`，写 `Related to #实际编号`。

产物：`fixtures/e3/mdfixer/README.md`、`fixed-md.json`、`oracle.md`，`target/` 下的故障 Makefile 变体 Patch、expected 说明和修复前日志。`macro/` 输入作为附录扩展。参考修复 Patch 由陆泓在下一个 PR 完成。

操作：选择真实 fzy 编译单元与项目头文件，制造同一个固定 MD。报告的源码 SHA、配置、目标和 Makefile 与样本完全一致。Target 在规则前置依赖中直接补头文件；Macro 在依赖变量中补头文件，并检查变量是否影响其他目标。

PR 2 作者陆泓，Reviewer 李新昊。分支 `test/e3-repair-validation`，标题 `test(mdfixer): 验证声明风格与拒绝恢复行为`，写 `Closes #实际编号`。

必交产物：Target 的参考 Patch、修复理由、`scripts/e3/verify_repair.sh` 和实际构建、功能、增量行为验证记录。扩展产物：其余声明风格的参考 Patch、`invalid.patch`、拒绝/恢复记录。

| 风格 | 验证重点 |
|---|---|
| Target | 在正确对象目标上补依赖，不改其他目标 |
| Macro | 保持变量展开语义，避免把头文件作为链接输入 |
| Hybrid | 保留直接依赖项，更新头文件变量 |
| Implicit | 恢复或使用编译器生成 `.d` 并加载；检查文件内容和之后的增量重编译 |

每种风格执行：

1. 原始故障样本先构建，再修改缺失头文件，记录漏重建。
2. 在干净副本执行 `git apply --check`，应用参考补丁。
3. 构建和功能测试通过后，再次修改同一头文件，执行普通 make，不 clean，确认对应对象重编译及功能结果更新。
4. 检查声明或 `.d` 中已存在目标到头文件的依赖。真实 BuildChecker 尚未实现时，称为人工依赖复核，不写“工具重检通过”。
5. 在另一个副本应用故意令构建或测试失败的候选，拒绝该候选，恢复原文件，再确认构建和功能测试通过。

Issue 正文任务验收：固定报告与 Makefile 对应；至少一套参考补丁改善了增量行为，不能只靠 clean 成功。附录扩展分别记录四种声明风格、无效候选及恢复的完成情况，未完成的扩展写入 open-items。固定报告和参考补丁是 ORACLE，不计入真实修复器成功率。

## 7. GitHub 操作：从任务到合并

### 创建任务和看板

李宇瀚创建 Milestone `E3 并行测试基线`，创建上述 6 个 Issue，并加入现有项目 Board。沿用 `Backlog / Ready / In progress / In review / Done`。依赖未完成的任务保留 Backlog，Issue 中写 `Blocked by #实际编号`。PR 开始 Review 后移动卡片，只有该 Issue 全部产物验收完成才进入 Done。

现有 Issue 模板名包含 E2，E3 可以直接用空白 Issue 填写以下正文，不必为开始工作先修改模板。

```md
## 目标
建立哪一项测试基线。

## 交付产物
- [ ] 样本和人工预期
- [ ] 命令与真实运行证据
- [ ] 独立复跑记录

## 验收条件
- [ ] 版本固定、样本可以重建
- [ ] 预期与实际结果分开
- [ ] 组内 Review 和复跑完成
- [ ] 相关 Actions 检查通过

## 依赖
Blocked by #实际编号，或无。
```

### 开发、PR、Review

1. 成员确认工作区无未处理改动，从最新 main 创建本计划指定的分支。已有改动先妥善保留，不覆盖、不直接清理。
2. 完成样本与说明，运行相关实验。每次运行保留新目录，把实际结果填写到对应证据文件。
3. 提交中文 Conventional Commit，例如 `test(buildchecker): 建立缺失依赖行为对照`。Commit 不写 E3-02 等内部任务编号。
4. 推送自己的分支，在仓库 Pull requests 创建 PR，base 选 main，填写交付路径、命令、结果、失败边界及实际 Issue 编号。
5. 一个 Issue 有两个 PR 时，第一个写 `Related to #编号`，最后一个写 `Closes #编号`。第一个合并后，第二位作者从更新后的 main 开始，避免复制前一个 PR 的改动。
6. 在 Reviewers 选择表中同组审核人。Reviewer 检查文件，并按 README 独立运行；在 Review 中写具体核验结果与证据链接。
7. 作者在原分支修正问题，补充运行记录并推送，继续使用同一个 PR。不要为了显示协作而编造 Review 问题。
8. 审核批准、相关检查通过且讨论解决后合并。通常沿用 Squash and merge；C0/C1/C2 的 PR 按前文保留真实历史。

PR 正文可用现有模板，将“接口交接”填写为“样本输入、人工预期、后续工具读取方式”。例如：

```md
## 修改内容
建立 fzy 的受控 MD/RD 案例，并记录自动依赖控制方式。

## 交付产物
- fixtures/e3/buildchecker/：Patch、预期发现及人工依据
- evidence/e3/buildchecker/<实际run-id>/：实际构建与行为记录

## 验证
- 命令：填写真正执行的命令
- 实际结果：填写增量/clean 对照、退出码及日志路径
- 尚未完成：填写剩余问题，或无

## 接口交接
- 输入：固定 fzy SHA 与故障 Patch
- 输出：TEAM_ORACLE 预期报告和 ACTUAL_RUN 记录
- 后续读取：BuildChecker 运行后与预期报告比较

## 关联 Issue
Related to #实际编号
```

### 并行时减少文件冲突

公共 fzy 上游快照由 E3-01 固定，其他作者优先交付 Patch，不在各工具 PR 中重复修改公共源码。C0/C1/C2 的实验源码另放在 `fixtures/e3/echecker/project/`，由李宇瀚、管泽昊、黄骢驰依次负责，保留三个真实版本；这一个实验副本用于 Git 历史复现，不作为四工具各自复制上游的惯例。

各作者只写自己工具下的案例与运行证据。AI_USAGE 采用各自添加一条记录；README、汇总表和最终 CI 由李宇瀚统一整理。发生重叠时先核对 diff，保留双方实际记录，不盲选整文件“传入更改”。

## 8. 检查和后续使用

CI 建议分两层：所有 PR 运行现有 E2 检查和 E3 材料检查；E3 Linux 行为检查对已交付样本运行构建、功能断言及修复对照。容器用例交付后再启用 Docker 验证。CI 生成日志可上传为 Actions Artifact，课程交付同时保留 Run 链接与所选文本证据。

材料检查验证 JSON、文件引用、版本映射和预期来源；它不能代替实际构建。strace 记录用于后续构图，也不能自动代表 BuildChecker 检测已经完成。

| 后续阶段 | 复用的 E3 基线 |
|---|---|
| E4 环境和密钥管理 | 已固定的系统、工具链、镜像与命令；密钥另外按课程要求管理 |
| E5 BuildChecker / DRAFT | MD/RD 人工答案，DRAFT 构建失败与成功条件 |
| E8 EChecker / MDFixer | C0/C1/C2 版本与命令变化，固定 MD、参考 Patch 与拒绝恢复 |
| E10 增量与全量比较 | 相同提交和配置下的预期，用真实报告比较一致性与耗时 |
| E12 真实数据联调 | 接入另一组真实数据，并按已核验的 libco 版本执行四工具集成 |

最终课程提交以仓库为主体：样本、人工依据、实际运行记录、Issue/PR/Review、真实版本和个人贡献都能通过路径及链接找到。截图只作辅助。
