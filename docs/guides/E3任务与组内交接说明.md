# E3 任务与组内交接说明

适用小组：A05、B05。项目协作仓库：`devops-build-toolchain-05`。

## 1. E3 要完成什么

E3 的主题是“并行测试基线”。课件要求准备能让工具接受的测试项目，写出预期结果和判断依据，保存真实运行结果；运行失败时也要记录版本、原因、尝试和下一步。

一份测试基线包括：固定的项目版本与环境、故障或变更、人工预期答案、可重跑命令和实际观察。后续实现四个工具时，用这些样本判断工具是否做对。

例如，源码读取一个头文件，Makefile 却没有声明它。这就是已知的缺失依赖样本。人工答案应该说明缺哪条边，运行证据应该展示只改头文件时是否漏重编译。之后 BuildChecker 的报告再与这个答案比较。

### 课件正文中的任务

| 小组 | 工具方向 | 本次必须准备的内容 |
|---|---|---|
| A05 | BuildChecker | 一个缺失声明 MD、一个冗余声明 RD，以及人工判断依据 |
| A05 | EChecker | 声明正确的 C0；新增 include 的 C1；只改编译命令的 C2；历史图和错误变化预期 |
| B05 | DRAFT | 项目源码与说明、构建命令、功能验证条件、可定位的构建失败记录 |
| B05 | MDFixer | 固定 MD 报告、对应版本 Makefile、期望 Patch，以及修复有效的判断方法 |
| 全员 | 共同交付 | README、环境、命令、真实结果或失败记录、仓库及 SHA、个人贡献、相互检查 |

MD 对应 `MISSING`，指实际需要但未声明的依赖；RD 对应 `REDUNDANT`，指声明了但在限定语义和执行范围内不需要的依赖。构建成功不等于依赖声明正确。

课件操作附录还给出 Linux 原始跟踪、四种声明风格和无效候选恢复。本组先完成正文任务，再按进度扩展。E3 不要求完成四个工具的自动实现；E12 再接入另一组真实数据联调。

### 结果如何区分

- 人工答案：`TEAM_ORACLE`，写在样本说明和 expected 文件中。
- 课程样例原始答案：如使用实验包，标记 `INSTRUCTOR_ORACLE`。
- 实际实验：`ACTUAL_RUN`，记录命令、退出码、输出或观察。
- 真实工具输出：工具实际运行后才能记录为 `TOOL_OUTPUT`。

人工报告不能当作检测工具报告，人工参考 Patch 不能当作自动修复结果。课件示例的数字输出属于微型项目，fzy 的答案必须依据实际改造和运行确定。

### 组员接到任务后需要完成什么

本次交付的是四个工具后续使用的测试基线，不是四个工具的完整实现。每个人都要把自己负责的案例整理成“输入是什么、预期是什么、为什么这样判断、如何运行、实际发生了什么”，不能只交一份源码或一张成功截图。

| 任务 | 交付与验收要点 |
|---|---|
| BuildChecker | MD、RD 各一个；给出目标与依赖边、人工依据；实际展示缺失依赖造成的漏重编译和冗余依赖造成的额外编译 |
| EChecker | C0、C1、C2 的真实提交与配置；给出依赖图及错误变化预期；分别核对新增 include 和仅编译命令变化的影响 |
| DRAFT | 固定项目源码、构建命令、功能输入与预期；准备可定位的失败候选与参考成功环境，记录实际构建和功能验证结果 |
| MDFixer | 固定 MD 报告和匹配的 Makefile、源码版本；给出参考 Patch；验证可应用、构建与功能通过，且只改相关头文件时能够正确重编译 |
| 共同材料 | 环境与工具版本、复现命令、实际结果或失败原因、Issue/PR/Commit SHA、Review 和个人贡献 |

执行顺序：先取得 E3-01 的环境和固定源码，阅读自己负责的案例说明，再在独立副本中制作样本并运行验证，最后通过 PR 交付，由 Reviewer 检查依据和复现结果。具体人员任务见第 4、5 节，依赖和协作步骤见第 6 节。

提交前逐项核对：

- [ ] 源码版本、配置和输入已固定，其他成员能够取得。
- [ ] 预期结果有人工依据，并与实际运行结果分开。
- [ ] 命令、退出码和关键观察完整，可从干净副本复现。
- [ ] 未通过或未完成的内容写明原因、影响和下一步。
- [ ] Issue、PR、真实 Commit SHA 和个人贡献可追溯。
- [ ] 完成对应 Review 和适用的自动检查；没有把尚未运行的工具结果写成已验证。

## 3. 每个成员如何准备环境

### Windows + Docker

安装并启动 Docker Desktop，使用 Linux 容器。取得包含 E3-01 文件的仓库后，在仓库根目录打开 PowerShell。

```powershell
docker version
docker build -t devops-e3-c0:ubuntu24.04 -f scripts/e3/Dockerfile.baseline scripts/e3
```

构建需要网络。Dockerfile 准备 Ubuntu 24.04、GCC、libc 开发头文件、GNU Make、Python、Git 和 strace。源码通过运行时挂载使用，不包含在环境镜像中。

在仓库根目录复跑现有 C0：

```powershell
docker run --rm --network none --workdir /repo --mount "type=bind,src=$((Get-Location).Path),dst=/repo" devops-e3-c0:ubuntu24.04 python3 scripts/e3/run_c0.py --operator 自己的姓名
```

此命令运行时无需网络。脚本在新的工作副本中构建、测试和核对依赖，最后输出 `EVIDENCE_DIR` 和 `STATUS`。

如果要手动执行自己的样本，在根目录启动实验 shell：

```powershell
docker run --rm -it --network none --workdir /repo --mount "type=bind,src=$((Get-Location).Path),dst=/repo" devops-e3-c0:ubuntu24.04 bash
```

进入后 `/repo` 就是仓库根目录。直接在 `/repo` 修改文件会同步到 Windows，因此构建和故障操作使用 `work/e3/` 下的新副本。

### 原生 Linux 或 WSL Linux

具备 GCC、libc 开发头文件、GNU Make、Python 3 和 Git 后，可直接在仓库根目录运行同一 Python 入口。Linux 跟踪扩展需要 strace。

本次记录的工具版本：Ubuntu 24.04、x86_64、GCC 13.3.0、GNU Make 4.3、Python 3.12.3、Git 2.43.0。不同成员记录自己实际使用的版本。基础镜像摘要固定，但软件包没有逐一锁版本；严格性能比较要使用同一实验镜像。

### 运行副本和基本命令

在 Linux shell 中，为每项实验使用一个不存在的新目录，例如孙鲲华的 MD/RD 副本：

```sh
mkdir -p work/e3
cp -a fixtures/e3/echecker/project work/e3/sun-md-rd-01
cd work/e3/sun-md-rd-01
make CC=gcc
make CC=gcc check
printf 'apple\nbanana\n' | ./fzy -e apple
```

复制前确认目标不存在，后续复跑换一个目录名。`make clean` 只在自己的运行副本中执行。原始快照和 C0 的固定文件不用于反复编译。

这些命令仅验证已有正确版本。制作故障后，必须补充针对故障的断言，不能只重复 apple 查询就宣布故障或修复符合预期。

### C1/C2 与现有 C0 检查的关系

当前 `check_baselines.py` 和 `run_c0.py` 只接受正确 C0：源码摘要固定，预期无 MISSING。直接把 project 改成 C1 后，现有 C0 检查会失败，这是检查范围不匹配。

因此 C1 PR 必须包含版本化验证的交接：让 C0 检查读取初始 C0 Commit 的固定源码或等价的固定 C0 副本，再增加独立 C1 用例；C2 同样增加自己的预期。原始快照、C0 摘要和 C0 人工答案继续保持，不把它们改成 C1 内容，也不删除正确 C0 断言来绕过门禁。

这项调整由管泽昊在 C1 PR 中提出，李宇瀚审核检查入口，孙鲲华审核实验含义。扩展检查只覆盖本阶段实际交付的版本，不要求一次实现全部检测工具。

E3-01 对应 Issue #17，其余 Issue 由仓库负责人按 Backlog 创建，得到真实编号后分配。

1. 从已合并的最新 main 创建自己的任务分支。E3-01 未合并时可以阅读和准备环境，正式分支从合并后的 main 开始。
2. 在对应 Issue 写清产物、验收、依赖。人员通过 Assignees 设置；PR 指定同组 Reviewer。
3. 实验在独立副本运行，提交样本、Patch、人工答案、命令和结果摘要。每次提交只关注一个任务，使用中文 Conventional Commit。
4. 同一 Issue 有两个 PR时，第一份写 `Related to #实际编号`，最终验收 PR 写 `Closes #实际编号`。C1 是中间 PR，C2 是最终 PR。
5. Reviewer 检查人工依据并实际复跑。作者在原分支修改、提交、推送，继续使用同一 PR。
6. 验收完成、Review 批准、Actions 通过后合并。C0/C1/C2 使用普通 merge 保留真实实验提交；初始源码 SHA 和后续文档 SHA 分开记录。

每个 PR 说明受影响样本、输入/预期、运行命令、实际结果、失败边界和关联 Issue。AI_USAGE 按实际参与填写，不用补造 Review 意见或贡献。
