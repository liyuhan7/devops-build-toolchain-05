# E4 操作与交付说明

使用分支：`chore/e4-environment`，须先由组长提交并推送。组长先在 ECS 分别跑通 A、B 两组，再让组员在各自学号目录按所属组重跑。当前分支的 ECS 结果尚未登记。

## 1. 每个人做什么

| 人员 | 工作内容 |
|---|---|
| 组长 | 检查 ECS 公共环境；首次运行 A/B 两组；处理公共问题；收齐个人证据与贡献说明，确认同版本重跑结果 |
| A 组每人 | 验证 BuildChecker 环境、单测、strace 冒烟，以及原项目 fzy C0/C1/C2、MD/RD 基线 |
| B 组每人 | 验证 DRAFT 环境、单测、预期失败冒烟，以及原项目 fzy 功能、MDFixer 参考修复、DRAFT 失败/参考容器 |
| 所有组员 | 验证扫描器负例；与同组另一人对照；提交本人实际工作和证据位置 |

组长跑通不能代替其他人运行。仅复跑环境的贡献据实写为环境验证，不写成算法实现。

## 2. 在 ECS 操作：每人一个学号目录

登录账号由组员共用，但每人（包括组长）在自己的 `~/<学号>/` 下独立克隆和运行，不共用一个仓库工作目录：

```text
~/<学号>/
  build-toolchain/       本人的仓库克隆
    .git/               本仓库的 Git 身份与版本
    .env                本人的本地配置
    work/e4/            本人的运行证据和交付说明
```

以下命令在 ECS 执行，将学号换成自己的。不要进入其他人的学号目录；已有本人克隆时检查版本和改动，不覆盖或重新初始化 Git。

```sh
STUDENT_ID='你的学号'
mkdir -p "$HOME/$STUDENT_ID"
cd "$HOME/$STUDENT_ID"
git clone --branch chore/e4-environment --single-branch https://github.com/liyuhan7/devops-build-toolchain-05.git build-toolchain
cd build-toolchain
git config --local user.name "$STUDENT_ID"
git config --local user.email "$STUDENT_ID@localhost"
git config --local --get user.name
git rev-parse HEAD
git status --short
```

确认显示本人学号、源码无改动后，在 `~/<学号>/build-toolchain/` 选择本人组别自检，再完整运行：

```sh
GROUP=A  # B 组改为 GROUP=B
make GROUP="$GROUP" doctor
make GROUP="$GROUP" all
```

Git 身份只在本人的克隆中设置，不使用 `--global`。镜像分别命名为 `e4-buildchecker:<学号>`、`e4-draft:<学号>`，Compose 项目也带学号；Docker 引擎和缓存由全组共用。

命令依次执行 `doctor → build → test → smoke → scan`。两组都会检查原项目契约、基线材料和回归测试；骨架单测预期 A 组 3 项、B 组 4 项通过。首次构建会下载镜像和依赖，先由组长顺序运行。

Docker 已可用时不重复安装；缺工具时由组长核对系统后按需使用 `setup/bootstrap_ubuntu.sh`。E4 无需真实 API Key，不填入密码或令牌；Git 身份只用 `--local`。B 使用 docker.sock 控制宿主机引擎，只构建课程项目，不清理他人的镜像和缓存。

## 3. 检查运行结果

成功时会打印目录 `work/e4/<组别>/<运行编号>/`，其完整位置是 `~/<学号>/build-toolchain/work/e4/<组别>/<运行编号>/`。单独执行 `doctor` 或 `scan` 的目录不算完整成功证据。失败记录原样保留，修正后重新运行；不要拼接多次日志作为一次成功记录。

| 文件 | 应确认的结果 |
|---|---|
| `source-sha.txt`、`worktree-status.txt` | 完整源码 SHA；运行前工作区无改动 |
| `env.json` | `problems=[]`；身份为本人学号 |
| `build.log`、`image.json`、`toolchain.lock` | 镜像构建成功；固定摘要、实际镜像 ID 和工具版本可定位 |
| `test.log` | 原项目检查、回归与本组骨架单测通过 |
| `smoke.json` | A：输出 `1`、打开 `config.h`、`passed=true`；B：非零构建退出码、`make: not found`、`passed=true` |
| `project-smoke/summary.json`、`project-smoke/evidence/` | 本组原项目案例全部通过，原始证据齐全；B 的 `pending_cases` 为空 |
| `secret-scan.txt` | 文件、Git 历史和本人镜像检查未发现问题 |

E4 的教学冒烟摘要不代替 E5 完整原始记录，也不证明四工具算法已经实现。

## 4. 扫描器负例与同组对照

在本人的 `~/<学号>/build-toolchain/` 中执行，沿用第 2 节的本人 `GROUP`。先确认 `git status --short` 无输出，且 `leak-demo.txt` 不存在；该假 Key 文件只暂存，不提交。

```sh
printf 'api_key = "%s%s"\n' 'sk-' 'demo1234567890abcdefghijk' > leak-demo.txt
git add leak-demo.txt
make GROUP="$GROUP" scan
NEGATIVE_CODE=$?
NEGATIVE_DIR=$(ls -td "work/e4/$GROUP/"* | head -n 1)
git restore --staged -- leak-demo.txt
rm -- leak-demo.txt
make GROUP="$GROUP" scan
CLEAN_CODE=$?
CLEAN_DIR=$(ls -td "work/e4/$GROUP/"* | head -n 1)
printf '负例：%s，退出码：%s\n清理后：%s，退出码：%s\n' "$NEGATIVE_DIR" "$NEGATIVE_CODE" "$CLEAN_DIR" "$CLEAN_CODE"
git ls-files .env
git status --short
```

预期负例报 `FOUND` 且退出码非零，清理后退出码为 0；`.env` 未被跟踪，假文件无残留。两个扫描目录不能代替完整 `make all` 的成功目录。

找同组另一人，确认完整 SHA 相同，比较两份 `toolchain.lock`、测试与冒烟结论。时间、进程号、镜像 ID 和日志行数可不同；工具版本或结论不同需要解释。同台 ECS 共用 Docker 缓存，应如实记录。

## 5. 每人交付与组长汇总

每人把以下内容交给组长：

1. **完整成功证据**：本人学号目录下 `make all` 的成功目录，提供绝对路径，含第 3 节全部文件及原项目原始证据。
2. **扫描验证**：负例与清理后目录、实际退出码。
3. **重跑对照**：对照同学、双方 SHA 和成功目录、比较结论及差异解释。
4. **个人工作说明**：保存为成功目录中的 `delivery.md`，按下列字段填写。

```text
姓名、学号、组别：
本人克隆绝对路径、所测完整 SHA：
完整成功目录、各阶段结论：
负例与清理后扫描目录、退出码：
对照同学、双方版本及目录、结论：
实际完成的工作、对应产物或证据：
遇到的问题、本人定位与处理、重跑结果：
协助了谁、具体做了什么：
AI 参与内容、本人确认和实际操作范围：
尚未完成的事项：
```

工作贡献写具体动作和证据，例如环境配置、独立复跑、结果核对、问题定位、修正验证、协助他人。未修改代码就不填写代码实现贡献；共同排障分别写明各自做的部分。没有问题或未完成项时据实写“无”。

组长收集以上个人材料，用下表汇总；日志和 `delivery.md` 留在各自学号目录，汇总时记录可访问的绝对路径，不让多人同时编辑一份个人说明。不要打包整个克隆目录，或收集 `.git`、`.env`、密钥、镜像缓存和编译产物。

| 姓名 / 学号 | 组别 | 所测 SHA | 成功目录 / delivery.md | 实际工作与贡献 | 扫描及对照结论 | 完成状态 / 待办 |
|---|---|---|---|---|---|---|
| | | | | | | |

最终汇总包含：实际服务器与镜像版本、所测提交、每人材料、同组对照、问题处理和未完成项。全部完成后再整理必要证据、创建 PR 并合并；不预填成员贡献或通过结果。
